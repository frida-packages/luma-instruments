# Mesh Finder test harness

`metal-target.m` and `opengl-target.c` render a scene offscreen, 60 times a
second, made of meshes whose counts and bounds are known, generated by
`meshes.h`: a cube, a UV sphere, a torus, a triangle-strip ribbon, an
octahedron and a pyramid, uploaded in a different way each:

| Mesh | Metal | OpenGL |
| --- | --- | --- |
| cube | interleaved position, normal and uv, 16-bit indices | the same, `glDrawElements` |
| sphere | positions alone, at an offset in their buffer, 32-bit indices | the same, with the indices at an offset too |
| torus | pulled by the shader, no vertex descriptor | interleaved, `glDrawRangeElements` |
| ribbon | triangle strip, not indexed | the same, `glDrawArrays` |
| octahedron | not indexed, four floats per position | the same, in a VAO it shares |
| pyramid | `setVertexBytes` | the shared VAO re-pointed between draws |
| cube | in private storage | — |
| torus | uploaded, never drawn | the same |
| sphere | uploaded after `SIGUSR1`, never drawn | the same, through `glMapBufferRange` |

Every pipeline and buffer is made before the harness attaches. The Metal
target rebuilds the cube's pipeline every two seconds, so a vertex descriptor
is seen too. Each target exports `mesh_finder_expectations`, a JSON list of
what should be found.

`harness.ts` loads the instrument with a fake `ctx`, raises `SIGUSR1` halfway
through and asks for a `scan`, then exports every mesh in the table as OBJ and
checks each expected one by its counts, bounding box and first vertices,
writing it to the output directory. It then shows each one and checks what
the viewer was handed: the counts, the size of the data, the first vertices,
and that every index is in range. Last, it disposes the instrument and
checks that every hooked function is back to its original bytes.
`explore.ts` is for other processes: it lists what was found after a number
of seconds and exports the five largest meshes.

Luma compiles instruments against its own frida-gum typings, which have
`Memory.findPointers`; the `frida` CLI's built-in ones may not. Link Luma's
into the repository (`node_modules` is ignored), generate the typings the app
would write, and build the targets outside the repository:

```sh
mkdir -p node_modules/@types
ln -s ~/src/luma/Agent/node_modules/@types/frida-gum node_modules/@types/frida-gum
python3 test/xpc-spy/generate-typings.py ~/src/luma mesh-finder test/mesh-finder/luma.d.ts
clang -fobjc-arc -framework Foundation -framework Metal -o /tmp/metal-target test/mesh-finder/metal-target.m
clang -framework OpenGL -o /tmp/opengl-target test/mesh-finder/opengl-target.c
```

Then, from the repository root, with the Python that has the `frida` module:

```sh
/tmp/metal-target &
python3 test/mesh-finder/run.py $! /tmp/meshes/metal
/tmp/opengl-target &
python3 test/mesh-finder/run.py $! /tmp/meshes/opengl
```

`run.py` exits non-zero if anything expected was missing or a hook was left
behind. To explore another process for 10 seconds, add the number of
seconds: `python3 test/mesh-finder/run.py <pid> /tmp/meshes/other 10`.

The Metal and OpenGL targets take a number of times to draw their scene each
frame, and print their frame times every two seconds; `/tmp/metal-target 300`
draws 2100 meshes a frame, for measuring what the hooks cost.

## Vulkan, on Linux

`vulkan-target.c` draws the same six meshes with Vulkan, offscreen, with no
surface or window: dynamic rendering into an image of its own. Every buffer
is made before the harness attaches, so those draws come out with their
triangle counts and no contents. On `SIGUSR1` the target reloads the scene
from new buffers, shifted 10 along x, the way a game loads a level, and
those are expected with their contents:

| Mesh | Vulkan |
| --- | --- |
| cube | interleaved position, normal and uv in host-visible memory, 16-bit indices; mapped, written and unmapped |
| sphere | positions alone at an offset, normals in a second binding, 32-bit indices at an offset; all staged into device-local memory |
| torus | `vkCmdSetVertexInputEXT` where the driver has it; persistently mapped, 32-bit indices |
| ribbon | triangle strip, `vkCmdDraw`, staged into device-local memory |
| octahedron | not indexed, four floats per position, stride from `vkCmdBindVertexBuffers2` |
| pyramid | `vkCmdDraw` from vertex 24 of the octahedron's buffer |
| torus | persistently mapped before attach, never drawn |
| sphere | staged into device-local memory after `SIGUSR1`, never drawn |

The sphere's and the ribbon's pipelines are made again every two seconds,
with their shader modules, so their vertex input and SPIR-V input names are
seen; the others keep pipelines made before attach.

Vulkan's headers are not part of every system; any checkout of
[Vulkan-Headers](https://github.com/KhronosGroup/Vulkan-Headers) does. With
`glslc`, from the repository root, building outside it:

```sh
git clone --depth 1 https://github.com/KhronosGroup/Vulkan-Headers /tmp/vulkan-headers
mkdir -p /tmp/vulkan-build
for shader in test/mesh-finder/vulkan-*.vert test/mesh-finder/vulkan-*.frag; do
    glslc -mfmt=c -o /tmp/vulkan-build/$(basename $shader).inc $shader
done
gcc -O2 -rdynamic -I/tmp/vulkan-headers/include -I/tmp/vulkan-build -o /tmp/vulkan-target test/mesh-finder/vulkan-target.c -lvulkan -lm
/tmp/vulkan-target &
python3 test/mesh-finder/run.py $! /tmp/meshes/vulkan
```

`/tmp/vulkan-target 300` draws 1800 meshes a frame and prints how long
recording them took.

## OpenGL and OpenGL ES, on Linux

`egl-target.c` draws the scene of `opengl-target.c` through EGL with no
window: in a surfaceless desktop OpenGL 3.3 core context, or in an OpenGL ES
3 context current on a pbuffer. The sphere's positions and indices are
copied into their buffers with `glCopyBufferSubData` from staging buffers.
It takes its functions from the library's exports, as a program linked
against it would call them, or from `eglGetProcAddress`, as glad does, and
the two are different functions:

```sh
gcc -O2 -rdynamic -o /tmp/egl-target test/mesh-finder/egl-target.c -lEGL -ldl -lm
for variant in "gl exports" "gl proc-address" "gles exports" "gles proc-address"; do
    /tmp/egl-target $variant &
    python3 test/mesh-finder/run.py $! /tmp/meshes/egl
    kill $!
done
```

A number after the variant, `/tmp/egl-target gles proc-address 300`, draws the
scene that many times a frame.

Both Linux targets are built with `-rdynamic`, which exports
`mesh_finder_expectations` for the harness. Mesa keeps a shader cache in
`~/.cache` unless `MESA_SHADER_CACHE_DIR` says otherwise. On Linux the
harness resolves the Vulkan driver's and OpenGL's functions the way the
instrument does, and checks that they are back to their original bytes after
dispose.
